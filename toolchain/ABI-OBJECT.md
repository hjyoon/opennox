# `Object` ABI 분리 기록

기준 소스는 upstream `b184030e76be2b681a7f6d2bcdef52b091d94b9b`, 도구체인은 `go1.26.5`, 원본 데이터 오라클은 `nox-2023-1003-01`이다. 이 문서는 64비트 포팅의 첫 구조체 변경을 재검토할 수 있도록 근거, 배치와 검증 결과를 기록한다.

## 변경 근거

원본 `nox_object_t`의 필드 64~84, 바이트 `256..339`는 맵 공간 인덱스용 32비트 포인터와 카운터였다. OpenNox에서는 맵 인덱스 구현이 이미 Go로 옮겨졌다.

- `68755bfc9`: 모든 맵 인덱스 함수를 `server` 패키지로 이동
- `6152e67c8`: 객체 인덱스 목록을 Go 포인터 기반 타입으로 정리

현재 트리에서 `ObjectIndex`/`ObjIndex*`의 실행 참조는 `server/map.go`와 제거 호출부에만 있었다. `legacy/defs.h`의 `field_64`~`field_84` 이외에는 이 이름을 사용하는 서버 객체 C 코드가 없다. 따라서 64비트 포인터가 원본의 84바이트 구간을 164바이트로 늘리게 둘 이유가 없고, 반대로 그 포인터를 `uint32`로 잘라 저장해서도 안 된다.

변경 후에는 다음처럼 분리한다.

1. C와 공유하는 `Object`에는 `[21]uint32` 크기의 `legacyMapIndex`를 그대로 남겨 원본 ABI32 영역과 후속 필드 위치를 보존한다.
2. 실제 `ObjectIndex` 포인터 연결 리스트는 `serverMap.objectIndex`가 소유하는 네이티브 `objectIndexState`에 둔다.
3. 객체가 맵에서 빠지거나 해제될 때 연결을 먼저 제거하고 사이드카를 삭제한다.
4. C의 `field_190`은 사용되지 않던 `uint32_t`가 아니라 Go의 `ScriptVars`와 같은 네이티브 `void*`로 선언한다. 32비트 배치는 변하지 않는다.
5. Go와 C 양쪽에 32/64비트 크기·핵심 오프셋 컴파일 타임 검사를 둔다.
6. 주소 `004E44F0`의 동기화 표시와 `004E4500`의 32개 상태 마스크 갱신은 각각 `field_38`, `field_37`, `field_140[32]` 명명 필드로 옮겼다. 원본 `+152`, `+148`, `+560` 접근과 `nox_object_t* -> int` 절단은 이 두 함수에서 제거됐다. 32개 개별 C 멤버도 실제 배열로 합쳐 멤버 경계를 넘는 포인터 산술을 없앴다.
7. 주소 `004E46F0`의 높이 변경과 `004E4880`의 애니메이션 프레임 표시는 `z`, `obj_class`, `field_33`, `field_140[32]` 명명 필드로 옮겼다. 높이 변경을 호출하면서 객체 포인터를 `int`로 자르던 8개 호출도 네이티브 객체 포인터 전달로 고쳤다.
8. 주소 `004E4670`의 활성 상태 변경은 `obj_flags`, `obj_class`, `field_140[32]` 명명 필드로 옮겼다. 세 직접 호출자와 함수 선언도 `nox_object_t*`를 전달하도록 바꿔 이 경로의 객체 포인터 절단을 제거했다.
9. 주소 `004E4780`/`004E4800`의 확장 상태 해제·설정은 기존 Go 구현을 원본 어셈블리와 분기별로 대조했다. 상태 비트 `1`의 동기화 생략, 이미 해제된 비트의 무쓰기 반환, 특수 클래스의 32개 슬롯 마스크와 일반 객체의 타입 상태 비교를 독립 계약 시험으로 고정했다. 세 C 파일의 직접 호출 28곳에서 두 번째 인수를 포인터로 넘기던 디컴파일 타입 오류도 제거했다. 다만 `int`로 객체를 받는 상위 호출자 체인은 후속 ABI 이식 범위다.
10. 주소 `004E48F0`의 버프 플래그 변경은 `Buffs`, 동기화 상태와 32개 슬롯 처리를 Go 메서드로 옮겼다. 플레이어 보호 CRC는 콜백 경계로 남기되 `data_update + 276`, `Player + 4612`를 읽던 원본 Win32 포인터 체인 대신 네이티브 `PlayerUpdateData.Player`와 `Player.ProtUnitBuffs`를 사용한다. C에는 원본의 one-past 반환 포인터를 보존하는 얇은 래퍼만 남겼다.
11. 주소 `004E4990`의 수식어 적용은 네 개의 포인터와 `field_16`을 이름 있는 `ModifierInitData`/`nox_modifier_attrs_t`로 옮겼다. 크기는 32비트 20바이트, 64비트 40바이트이고 `field_16`은 각각 `+16`, `+32`다. 원본의 강제 적용 조건, 빈 입력 조기 반환, 지연 `TeamBase` 조회, 적용 가능 클래스, 다섯 필드 복사, 동기화와 32개 상태 슬롯 갱신 및 세 가지 반환값을 그대로 보존했다. 맵 생성·직렬화·퀘스트·보상·기본 장비·리스폰의 직접 호출자는 더 이상 20바이트 임시 배열이나 `init_data + 692`를 `int*`로 넘기지 않는다.
12. 주소 `004E4A70`의 질량 읽기는 원본 `flds [object+0x78]`를 `obj->mass`로 바꾸고 인수를 `const nox_object_t*`로 타입화했다. C와 Go 양쪽에 32비트 `+120`, 64비트 `+124` 배치 단정을 추가해 첫 네이티브 포인터 뒤의 필드 이동도 명시했다. 직접 호출자는 모두 객체 포인터임을 표시했지만, 아직 `int`로 객체를 받는 상위 충돌 함수들은 후속 ABI 이식 범위다.
13. 주소 `004E4A80`의 버프 플래그 읽기는 과거 소스의 `sub_4E4A80(int)`가 미사용 코드 정리에서 삭제된 이력과 원본 xref 부재를 함께 확인한 뒤 완전 복원 범위에 다시 넣었다. 원본 `mov eax,[object+0x154]; ret`를 `uint32_t` 반환과 `const nox_object_t*` 입력의 `nox_xxx_objectGetBuffs_4E4A80`으로 타입화해 포인터 절단 없이 `obj->buffs`를 읽는다.
14. 주소 `004E4A90`의 NPC 색 변경은 원본 `data_update + 2076 + 3*index`의 3바이트 복사를 네이티브 `MonsterUpdateData.Color[index]` 접근으로 옮겼다. C 경계에는 정확히 3바이트인 `nox_color3_t`를 두고, 원본과 같은 `field_140` one-past 포인터 반환을 얇은 래퍼에서 보존했다. 유효 호출 계약인 색 인덱스 `0..5`와 특수·일반 객체의 상태 슬롯 분기는 Go 계약 시험과 C 힙 왕복 시험으로 고정했다. 두 직접 호출은 객체와 색 포인터를 타입화했지만, 이를 포함하는 대형 XFer 함수의 상위 `int` 객체·업데이트 데이터 경로는 아직 이식 범위다.
15. 주소 `004E4B20`의 NPC 장비 상태 변경은 원본 `data_update + 2056/+2060`을 이름 있는 `MonsterUpdateData.WeaponEquipFlags`/`ArmorEquipFlags`로 옮겼다. `a3 == 1`만 장착이고 다른 모든 값은 해제인 계약, 무기·완드와 그 밖의 아이템 조회 분기, `NeedSync` 선행 순서, OR/AND-NOT 갱신, 세 특수 클래스와 일반 객체의 32개 슬롯 및 one-past 반환을 보존했다. C 함수의 두 객체 인수는 네이티브 포인터가 됐고 다섯 직접 호출도 타입을 명시하지만, 이 중 네 상위 장착 함수는 아직 객체 주소를 `int`로 보관한다.
16. 주소 `004E4C00`/`10`/`30`/`50`/`80`의 nullable getter는 각각 `NetCode`, 16비트 `TypeInd`, `InitData` 포인터, 타입 정의의 32비트 `InitDataSize`, `IDPtr`를 읽으며 null 객체 또는 누락 타입에는 0을 반환한다. 기존 `004E4C30`과 `004E4C80`의 `int` 반환은 64비트에서 포인터를 절단하므로 `void*`와 `const char*`로 바로잡았다. 보호 CRC 호출부도 세 정수 필드만 고정폭 값으로 유지하고 두 데이터 주소는 네이티브 포인터로 전달한다. C/Go 양쪽에 `IDPtr`, `TypeInd`, `NetCode`, `InitData`의 32/64비트 오프셋 단정을 두었다.
17. 주소 `004E4C90`은 키 `1`, `2`, `4`, `8`, `0x40`, `0x80`, `0x200`, `0x400`에 대해 애니메이션 프레임, 현재/기본 체력, enabled 비트, 확장 상태, 높이, 버프, 장비 가능 클래스, NPC 클래스를 질의한다. 본문 254바이트와 비연속 40바이트 dispatch table을 각각 봉인했다. 높이는 원본 x87 C3만 검사하므로 `+0`, `-0`, NaN이 모두 false이고, 기존 Go의 `!= 0`이 NaN을 true로 만들던 차이를 수정했다. Go `uint`/`int` CGo 경계를 `uint32`와 C `unsigned int`/`int`로 고정하고 이름을 `HasSyncData`로 바꿨다. 직접 호출자 `004DE410`도 `uint32_t*`/`int` 객체 주소 대신 `nox_object_t*`와 명명 필드를 사용한다.
18. 주소 `004E4DC0`/`004E4DD0`은 각각 상수 `0x1429`/`0x490`을 `00402000`의 원본 CRT 시드 함수에 넘기는 12바이트 래퍼다. 과거 복원 소스에도 같은 두 `nox_platform_srand` 호출이 있었고 `6b40fb6cf`에서 미사용 시드 함수로 삭제된 이력을 확인했다. 원본 실행 코드에는 두 래퍼로 향하는 직접 호출이 없지만 완전 복원 범위에는 포함하며, 현재의 Go 기반 플랫폼 RNG 경계에 고정폭 상수를 전달하도록 되살렸다.
19. 주소 `004E4DE0`은 기존 중요 패킷 할당 클래스를 해제하고, 원본 전역의 64바이트 플레이어 카운터와 32×12바이트 rate-control 레코드를 0으로 만든 뒤 각 레코드를 `{resends=1, interval=2, rate=current}`로 초기화한다. 원본 `0x7528d8`은 레코드 배열 끝과 할당 클래스 포인터 슬롯을 겸하므로, 고정폭 레코드는 원본 메모리에 남기고 런타임 할당 포인터는 네이티브 사이드카로 분리했다. 32비트에서는 원본 슬롯에 포인터를 미러링하고 64비트에서는 0으로 유지한다. 원본의 `(int)pointer` 종료 비교는 명시적인 32회 반복으로 바꿨다.
20. 주소 `004E4E50`은 선택한 12바이트 rate-control 레코드의 `threshold`와 `lower_threshold`를 계산한다. 모드가 정확히 `1`일 때만 현재 업데이트 비율을 제수로 쓰고, 그 밖에는 `1`을 쓴다. 원본 x86의 `DIV`처럼 유효 설정에서 제수는 0이 아니어야 한다. `interval > 2`이면 FPS를 두 번 독립적으로 읽으며 각 경로에서 나눗셈을 곱셈보다 먼저 수행한다. 모든 곱은 `uint32_t`로 래핑하고 반환 비트만 signed 32비트로 해석하도록 고정했다.

이는 원본 메모리 이미지를 64비트에서도 그대로 쓰는 방식이 아니다. 고정폭 원본 슬롯과 네이티브 런타임 포인터를 명시적으로 분리하는 첫 단계다.

## 통과한 검증

1. Linux/386 Go `server` 패키지 전체 테스트 통과. 새 테스트는 기본/대형 객체 삽입 순서, 네 개 파티션 슬롯 제한, 제거 후 연결 해제와 객체 해제 시 사이드카 삭제를 확인한다.
2. Linux/386 cgo로 클라이언트, HD 클라이언트, 서버를 모두 링크했다.
3. 세 산출물은 모두 ELF 32-bit i386, Go `1.26.5`이고 `-h` 시작 시험이 종료 코드 0으로 통과했다.
4. O0 전체 원본 트리 검증과 O1 NXZ 50개 쌍 비교를 변경 후 다시 통과했다.
5. Darwin/ARM64에서 Go `Object` 핵심 오프셋을 `layoutaudit`로 추출하고 네이티브 Clang이 계산한 C 오프셋과 대조했다.
6. Linux/386에서 실제 C `004E44F0`/`004E4500`과 Go `NeedSync`/`Sub_4E4500`에 같은 입력을 주는 차등 테스트를 통과했다. 상태 마스크의 set/clear 양 경로, 비트 0과 31, 32개 슬롯 전부와 인접 필드 비변조를 확인한다.
7. `004E46F0` 높이 변경은 일반 변경, 동일값, `-0/+0`, source/target NaN을 시험했다. 원본 x87은 비교 결과 C3만 검사하므로 NaN도 변경하지 않는데, 기존 의사 C의 `!=`는 NaN을 변경하던 차이를 찾아 원본 의미로 고쳤다.
8. `004E4880` 애니메이션 프레임 표시는 프레임·동기화 필드, 32개 상태 슬롯과 인접 필드 비변조를 C/Go 차등 시험으로 확인했다.
9. `004E4670` 활성 상태 변경은 enable/disable 양쪽, 기존 플래그 보존, 동기화 필드, 32개 상태 슬롯, 인접 필드 비변조와 원본의 one-past 반환 포인터를 C/Go 차등 시험으로 확인했다.

## 아직 통과하지 않은 범위

- C에 남은 `nox_object_t` 원시 숫자 오프셋 접근은 이름 있는 필드 접근 또는 Go 경계 함수로 계속 옮겨야 한다. 구조체의 명명 필드 배치가 맞는 것만으로 원시 `+444` 같은 코드가 64비트에서 안전해지지는 않는다.
- 일부 보상 정의와 원본 메모리 테이블에는 수식어 설명자 주소가 아직 `uint32` 슬롯으로 남아 있다. `004E4990`의 직접 경계는 네이티브 포인터지만 이 생산자 테이블은 별도 ID/포인터 분리가 필요하며, `int` 객체 인수를 받는 상위 호출자도 계속 이식해야 한다.
- `004E4A90`을 직접 호출하는 `nox_xxx_XFerMonster_528DB0`과 `nox_xxx_XFerNPC_52ADE0`은 호출 경계만 타입화됐다. 두 대형 함수에는 객체와 `data_update`를 `int`에 담거나 원본 `+2076`을 직접 계산하는 경로가 남아 있으므로 전체 XFer 경로는 아직 64비트 안전하다고 판정하지 않는다.
- `004E4B20`의 직접 경계와 `sub_4ED0C0` 호출은 네이티브 객체 포인터지만 `nox_xxx_equipWeaponNPC_53A030`, `nox_xxx_NPCEquipWeapon_53A2C0`, `sub_53E3A0`, `nox_xxx_NPCEquipArmor_53E520`은 여전히 상위 객체 주소를 `int`에 보관한다. `MonsterUpdateData` 전체도 앞부분의 런타임 포인터 때문에 64비트 공유 배치 분리가 남아 있다.
- 주소 순서상 다음 함수 `004E4ED0`은 32명의 중요 패킷 카운터(각 16비트)를 0으로 초기화한다. 정확한 64바이트 쓰기 범위와 인접 메모리 비변조를 원본과 대조해야 한다.
- Darwin/ARM64 전체 `server` 패키지는 `PlayerJournal`, `MinimapItem`, `EquipmentData`, `Player`, `NPC`의 고정 32비트 검사에서 계속 중단된다. 이것이 다음 구조체 분리 범위다.
- Linux/AMD64·ARM·ARM64 및 Windows/macOS 제품 링크·실행은 아직 합격 처리하지 않는다.
- 원본 `GAME.EXE`와의 결정론적 프레임 상태, 패킷, 저장 파일 양방향 비교는 O2/O3 도구가 마련된 뒤 수행한다.
