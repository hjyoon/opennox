# Go 1.26.5 멀티아키텍처 포팅 인벤토리

이 문서는 `port/go1.26-multiarch` 브랜치에서 실제로 확인한 포팅 상태다. 기준 소스는 upstream 커밋 `b184030e76be2b681a7f6d2bcdef52b091d94b9b`, 도구체인은 정확히 `go1.26.5`이다. 숫자는 2026-08-13의 작업 트리 기준이며, 정적 검색 후보와 확인된 결함을 구분한다.

## 현재까지 통과한 단계

1. 보관본 `nox/`의 일반 파일 1,556개, 570,653,750바이트를 전부 SHA-256 매니페스트로 봉인했다. 누락·추가·변조 파일과 심볼릭 링크를 거부하며 트리 SHA-256은 `161675279c5a9a6e5e8da4ae539ad80f9033d608b32ad620a052866ecc1e61b7`이다.
2. `src/go.mod`, 빌드 래퍼와 Docker 빌드 단계를 Go `1.26.5`로 고정했다.
3. 수정 전 Linux/386 클라이언트·HD 클라이언트·서버를 빌드하고 세 바이너리의 `-h` 시작 시험을 통과했다. 상세 값은 `BASELINE-linux-386.md`에 있다.
4. `internal/noxbuild`가 9개의 유효한 Go 1.26 대상 tuple과 ISA 기준값을 검증하고, 대상별 C/C++ 컴파일러를 선택하도록 변경했다.
5. Darwin용 보호 페이지 할당과 소켓 대기 바이트 조회 백엔드를 추가했다.
6. 32비트 C 포인터에 종속된 NXZ 압축·해제를 순수 Go 구현으로 교체했다.
7. `Object`의 맵 인덱스 포인터를 네이티브 `serverMap` 사이드카로 옮기고 C 공유 영역에는 원본 필드 64~84와 같은 `[21]uint32`만 남겼다. 64비트 Go/C 공유 코어는 모두 912바이트로 맞았고 32비트 772바이트 코어와 780바이트 전체 Go 객체는 변하지 않았다. 상세 대조는 `ABI-OBJECT.md`에 있다.
8. 원본 `GAME.EXE`의 서른 함수와 한 dispatch table, 합계 서른한 범위를 VA·길이·SHA-256으로 봉인하고 `Object`의 첫 원시 오프셋 접근을 명명 필드로 옮겼다. ## 첫 64비트 컴파일에서 확인된 ABI 단절

Darwin/ARM64에서 서버를 실제 컴파일하면 `server` 패키지의 32비트 크기 검사에서 먼저 중단된다. 이 검사는 잡음이 아니라 C와 Go가 동일 메모리를 직접 해석한다는 안전장치다.

| Go 타입 | 원본 32비트 크기 | 첫 Darwin/ARM64 진단 | 현재 Darwin/ARM64 |
| --- | ---: | ---: | ---: |
| `ObjectIndex` | 16 | 32 | 32 |
| `Object` 본체와 확장 핸들 | 780 | 1,016 | 928 |
| `PlayerJournal` | 76 | 88 | 88 |
| `MinimapItem` | 16 | 32 | 32 |
| `EquipmentData` | 24 | 48 | 48 |
| `Player` | 4,828 | 6,136 | 6,136 |
| `NPC` | 1,316 | 2,592 | 2,592 |

표의 `ObjectIndex`는 이제 독립된 네이티브 사이드카에서만 사용하므로 크기 차이가 C 공유 `Object` 후속 필드를 밀지 않는다. `Object` 전체 928바이트 중 C와 공유하는 접두사 912바이트는 네이티브 C `nox_object_t`와 핵심 필드 오프셋이 일치하며, 나머지 16바이트는 Go 전용 핸들이다.

`Player`는 첫 포인터 전까지 배치가 같지만 `PlayerUnit` 뒤부터 어긋난다. ARM64에서 `info`는 2,185가 아니라 2,189, `Frame3596`은 3,596이 아니라 4,880, `Field4580`은 4,580이 아니라 5,880에 놓인다.

더 중요한 문제는 `Player.C()`와 `Object.CObj()`가 Go 구조체 주소를 그대로 C의 `nox_playerInfo*`, `nox_object_t*`로 넘긴다는 점이다. C 코드에는 여전히 `+276`, `+444`, `+2056`, `+3644` 같은 원본 바이트 오프셋 접근이 있다. 따라서 크기 검사와 C `_Static_assert`만 비활성화하면 컴파일 단계는 더 진행될 수 있어도 올바른 포트가 아니며, 런타임 메모리 손상을 만든다.

## 구조체 분리 원칙

각 구조체와 필드를 다음 세 영역 중 하나로 옮긴다.

1. `Legacy*32`: 원본 실행 파일 분석과 호환 검사용 고정폭 바이트 배치. 런타임 포인터를 넣지 않는다.
2. 네이티브 런타임 타입: Go/C의 실제 포인터, `size_t` 또는 Go `int`를 사용한다. 원본 바이트 오프셋을 API로 노출하지 않는다.
3. 파일·네트워크 DTO: 명시적인 little-endian 정수와 encode/decode 함수만 사용한다.

C가 장기간 보관해야 하는 Go 객체 참조는 `runtime/cgo.Handle`을 직접 와이어 형식에 넣지 않고, 세대 번호를 포함한 프로젝트 정수 핸들 테이블을 통과시킨다. C 할당 객체라면 네이티브 C 포인터를 사용할 수 있지만 파일·패킷·원본 ABI32 필드로 직렬화하지 않는다.
