# `Object` ABI 분리 기록

기준 소스는 upstream `b184030e76be2b681a7f6d2bcdef52b091d94b9b`, 도구체인은 `go1.26.5`, 원본 데이터 오라클은 `nox-2023-1003-01`이다. 이 문서는 64비트 포팅의 첫 구조체 변경을 재검토할 수 있도록 근거, 배치와 검증 결과를 기록한다.

## 변경 근거

원본 `nox_object_t`의 필드 64~84, 바이트 `256..339`는 맵 공간 인덱스용 32비트 포인터와 카운터였다. OpenNox에서는 맵 인덱스 구현이 이미 Go로 옮겨졌다.

- `68755bfc9`: 모든 맵 인덱스 함수를 `server` 패키지로 이동
- `6152e67c8`: 객체 인덱스 목록을 Go 포인터 기반 타입으로 정리

현재 트리에서 `ObjectIndex`/`ObjIndex*`의 실행 참조는 `server/map.go`와 제거 호출부에만 있었다. `legacy/defs.h`의 `field_64`~`field_84` 이외에는 이 이름을 사용하는 서버 객체 C 코드가 없다. 따라서 64비트 포인터가 원본의 84바이트 구간을 164바이트로 늘리게 둘 이유가 없고, 반대로 그 포인터를 `uint32`로 잘라 저장해서도 안 된다.

변경 후에는 다음처럼 분리한다.

1. C와 공유하는 `Object`에는 `[21]uint32` 크기의 `legacyMapIndex`를 그대로 남겨 원본 ABI32 영역과 후속 필드 위치를 보존한다.
2. 실제 `ObjectIndex` 포인터 연결 리스트는 `serverMap.objectIndex`가 소유하는 네이티브 `objectIndexState`에 둔다.
3. 객체가 맵에서 빠지거나 해제될 때 연결을 먼저 제거하고 사이드카를 삭제한다.
4. C의 `field_190`은 사용되지 않던 `uint32_t`가 아니라 Go의 `ScriptVars`와 같은 네이티브 `void*`로 선언한다. 32비트 배치는 변하지 않는다.
5. Go와 C 양쪽에 32/64비트 크기·핵심 오프셋 컴파일 타임 검사를 둔다.
6. 주소 `004E44F0`의 동기화 표시와 `004E4500`의 32개 상태 마스크 갱신은 각각 `field_38`, `field_37`, `field_140[32]` 명명 필드로 옮겼다. 원본 `+152`, `+148`, `+560` 접근과 `nox_object_t* -> int` 절단은 이 두 함수에서 제거됐다. 32개 개별 C 멤버도 실제 배열로 합쳐 멤버 경계를 넘는 포인터 산술을 없앴다.
7. 주소 `004E46F0`의 높이 변경과 `004E4880`의 애니메이션 프레임 표시는 `z`, `obj_class`, `field_33`, `field_140[32]` 명명 필드로 옮겼다. 높이 변경을 호출하면서 객체 포인터를 `int`로 자르던 8개 호출도 네이티브 객체 포인터 전달로 고쳤다.
8. 주소 `004E4670`의 활성 상태 변경은 `obj_flags`, `obj_class`, `field_140[32]` 명명 필드로 옮겼다. 세 직접 호출자와 함수 선언도 `nox_object_t*`를 전달하도록 바꿔 이 경로의 객체 포인터 절단을 제거했다.

이는 원본 메모리 이미지를 64비트에서도 그대로 쓰는 방식이 아니다. 고정폭 원본 슬롯과 네이티브 런타임 포인터를 명시적으로 분리하는 첫 단계다.

## 통과한 검증

1. Linux/386 Go `server` 패키지 전체 테스트 통과. 새 테스트는 기본/대형 객체 삽입 순서, 네 개 파티션 슬롯 제한, 제거 후 연결 해제와 객체 해제 시 사이드카 삭제를 확인한다.
2. Linux/386 cgo로 클라이언트, HD 클라이언트, 서버를 모두 링크했다.
3. 세 산출물은 모두 ELF 32-bit i386, Go `1.26.5`이고 `-h` 시작 시험이 종료 코드 0으로 통과했다.
4. O0 전체 원본 트리 검증과 O1 NXZ 50개 쌍 비교를 변경 후 다시 통과했다.
5. Darwin/ARM64에서 Go `Object` 핵심 오프셋을 `layoutaudit`로 추출하고 네이티브 Clang이 계산한 C 오프셋과 대조했다.
6. Linux/386에서 실제 C `004E44F0`/`004E4500`과 Go `NeedSync`/`Sub_4E4500`에 같은 입력을 주는 차등 테스트를 통과했다. 상태 마스크의 set/clear 양 경로, 비트 0과 31, 32개 슬롯 전부와 인접 필드 비변조를 확인한다.
7. `004E46F0` 높이 변경은 일반 변경, 동일값, `-0/+0`, source/target NaN을 시험했다. 원본 x87은 비교 결과 C3만 검사하므로 NaN도 변경하지 않는데, 기존 의사 C의 `!=`는 NaN을 변경하던 차이를 찾아 원본 의미로 고쳤다.
8. `004E4880` 애니메이션 프레임 표시는 프레임·동기화 필드, 32개 상태 슬롯과 인접 필드 비변조를 C/Go 차등 시험으로 확인했다.
9. `004E4670` 활성 상태 변경은 enable/disable 양쪽, 기존 플래그 보존, 동기화 필드, 32개 상태 슬롯, 인접 필드 비변조와 원본의 one-past 반환 포인터를 C/Go 차등 시험으로 확인했다.

## `GAME.EXE` 직접 대조 근거

전체 파일 SHA-256이 `0040e2c0683b4d73a5fb976e400d5087dca680df2b195c9e27f8edbda2d4974a`인 보관본을 기준으로 다음 코드 범위를 `game-exe-functions.json`에 봉인했다.

`field_38`, `field_37`, `obj_flags`, `z`, `field_33`, `field_140[32]`은 원본 32비트 배치에서 각각 `+0x98`, `+0x94`, `+0x10`, `+0x68`, `+0x84`, `+0x230`이다. 따라서 명명 필드로 바꾼 C 코드와 Go 기준 구현의 분기·폭·반복 횟수는 이 원본 범위와 일치한다. `make oracle-code-verify`가 전체 오라클 ID, `GAME.EXE` 해시, PE 형식·이미지 베이스·실행 섹션과 다섯 코드 해시를 매번 다시 검사한다.

Linux/386 산출물 SHA-256은 다음과 같다. 클라이언트 두 개는 `ObjectIndex` 사이드카 분리 직후, 서버는 다섯 함수의 원본 대조·필드화·차등 테스트를 포함한 깨끗한 커밋 `a802c6691`에서 생성했다. 이 값은 작업 단계의 회귀 식별자이지 릴리스 해시가 아니다.

## 아직 통과하지 않은 범위

- C에 남은 `nox_object_t` 원시 숫자 오프셋 접근은 이름 있는 필드 접근 또는 Go 경계 함수로 계속 옮겨야 한다. 구조체의 명명 필드 배치가 맞는 것만으로 원시 `+444` 같은 코드가 64비트에서 안전해지지는 않는다.
- Darwin/ARM64 전체 `server` 패키지는 `PlayerJournal`, `MinimapItem`, `EquipmentData`, `Player`, `NPC`의 고정 32비트 검사에서 계속 중단된다. 이것이 다음 구조체 분리 범위다.
- Linux/AMD64·ARM·ARM64 및 Windows/macOS 제품 링크·실행은 아직 합격 처리하지 않는다.
- 원본 `GAME.EXE`와의 결정론적 프레임 상태, 패킷, 저장 파일 양방향 비교는 O2/O3 도구가 마련된 뒤 수행한다.
