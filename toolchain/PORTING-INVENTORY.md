# Go 1.26.5 멀티아키텍처 포팅 인벤토리

이 문서는 `port/go1.26-multiarch` 브랜치에서 실제로 확인한 포팅 상태다. 기준 소스는 upstream 커밋 `b184030e76be2b681a7f6d2bcdef52b091d94b9b`, 도구체인은 정확히 `go1.26.5`이다. 숫자는 2026-08-12의 작업 트리 기준이며, 정적 검색 후보와 확인된 결함을 구분한다.

## 현재까지 통과한 단계

1. 보관본 `nox/`의 일반 파일 1,556개, 570,653,750바이트를 전부 SHA-256 매니페스트로 봉인했다. 누락·추가·변조 파일과 심볼릭 링크를 거부하며 트리 SHA-256은 `161675279c5a9a6e5e8da4ae539ad80f9033d608b32ad620a052866ecc1e61b7`이다.
2. `src/go.mod`, 빌드 래퍼와 Docker 빌드 단계를 Go `1.26.5`로 고정했다.
3. 수정 전 Linux/386 클라이언트·HD 클라이언트·서버를 빌드하고 세 바이너리의 `-h` 시작 시험을 통과했다. 상세 값은 `BASELINE-linux-386.md`에 있다.
4. `internal/noxbuild`가 9개의 유효한 Go 1.26 대상 tuple과 ISA 기준값을 검증하고, 대상별 C/C++ 컴파일러를 선택하도록 변경했다.
5. Darwin용 보호 페이지 할당과 소켓 대기 바이트 조회 백엔드를 추가했다.
6. 32비트 C 포인터에 종속된 NXZ 압축·해제를 순수 Go 구현으로 교체했다.
7. `Object`의 맵 인덱스 포인터를 네이티브 `serverMap` 사이드카로 옮기고 C 공유 영역에는 원본 필드 64~84와 같은 `[21]uint32`만 남겼다. 64비트 Go/C 공유 코어는 모두 912바이트로 맞았고 32비트 772바이트 코어와 780바이트 전체 Go 객체는 변하지 않았다. 상세 대조는 `ABI-OBJECT.md`에 있다.
8. 원본 `GAME.EXE`의 스물네 함수와 한 dispatch table, 합계 스물다섯 범위를 VA·길이·SHA-256으로 봉인하고 `Object`의 첫 원시 오프셋 접근을 명명 필드로 옮겼다. C/Go 차등 시험에서 기존 높이 변경 의사 C의 NaN 동작 차이를 찾아 원본 x87 의미로 수정했다. `004E4670`은 활성 상태 플래그와 상태 슬롯을 필드화하고 세 직접 호출자의 포인터 절단을 제거했다. 대칭 함수 `004E4780`/`004E4800`은 원본 어셈블리의 조기 반환·특수 클래스·32개 슬롯 분기를 독립 Go 계약 시험으로 고정하고, 28개 C 호출에서 상태값을 포인터로 넘기던 잘못된 타입을 제거했다. `004E48F0`은 버프 상태와 보호 CRC 갱신 순서를 Go 계약으로 옮겨 `data_update + 276`, `Player + 4612`의 32비트 포인터 체인을 네이티브 `Player` 참조로 교체했다. `004E4990`은 20/40바이트 수식어 구조체와 60/104바이트 리스폰 레코드를 분리하고 맵·직렬화·퀘스트·보상·기본 장비·리스폰 직접 호출을 네이티브 포인터 폭으로 바꿨다. `004E4A70`은 `+0x78` 원시 읽기를 `mass` 필드로 바꾸고 API를 `const nox_object_t*`로 타입화했다. 삭제됐던 `004E4A80` 버프 getter는 `uint32_t`/네이티브 객체 포인터로 복원했다. `004E4A90`은 3바이트 NPC 색을 네이티브 `MonsterUpdateData.Color`로 쓰게 했다. `004E4B20`은 무기·방어구 장비 비트를 이름 있는 업데이트 필드로 옮기고 두 분류·장착/해제·동기화 분기를 C/Go 계약으로 고정했다. `004E4C00`/`10`/`30`/`50`/`80`은 null 분기와 정확한 16/32비트·포인터 반환을 고정하고, `InitData`와 ID를 `int`로 반환하던 64비트 절단을 제거했다. `004E4C90`은 여덟 동기화 키와 dispatch table을 계약화하고 NaN 높이 차이, CGo 네이티브 폭과 직접 호출자의 객체 포인터 절단을 수정했다. `004E4DC0`/`004E4DD0`은 과거 미사용 정리에서 삭제됐던 고정 시드 래퍼를 현재 플랫폼 RNG 경계에 복원했다. `004E4DE0`은 32개 고정폭 rate-control 레코드와 네이티브 할당 클래스 포인터를 분리하고 포인터-정수 종료 비교를 제거했다. `004E4E50`은 원본의 업데이트 비율 나눗셈, 독립 FPS 로드와 unsigned 임계값 오버플로를 이름 있는 레코드와 계약 시험으로 고정했다. `004E4ED0`은 32개의 16비트 플레이어 카운터와 정확한 64바이트 초기화 범위를 타입·계약 시험으로 고정했다.

NXZ 검증에는 먼저 O0 무결성을 통과한 설치 보관본의 `.nxz` 맵 50개를 사용했다. 모든 파일을 해제해 대응 `.map`의 길이와 SHA-256을 비교했고, 새 압축기로 다시 압축·해제한 결과도 전부 일치했다. 엄격 모드는 정확히 50개 쌍을 검사하지 않으면 실패한다. 별도 fixture는 64 KiB 윈도 래핑과 기존 압축기의 500,000바이트 청크 경계를 넘는다. `legacy/cnxz` 테스트 바이너리는 `CGO_ENABLED=0`으로 다음 9개 tuple에서 모두 컴파일됐다.

```text
linux/386       linux/amd64       linux/arm       linux/arm64
windows/386     windows/amd64     windows/arm64
darwin/amd64    darwin/arm64
```

## 재현 가능한 정적 검색

저장소 루트에서 다음 명령을 실행한다.

```bash
./scripts/portability-audit.sh
./scripts/go.sh -C src run ./internal/layoutaudit \
  -os=darwin -arch=arm64 -fields=Object,Player
```

첫 명령은 후보 수를 다시 집계하고, 두 번째 명령은 지정한 대상의 Go 구조체 크기와 선택한 모든 필드 오프셋을 출력한다. `layoutaudit`는 미완성 대상의 타입 오류 수를 함께 표시하지만 진단을 계속한다. 출력은 C 배치와 별도로 대조해야 하며 그 자체가 ABI 호환 판정은 아니다.

현재 출력은 다음과 같다.

| 분류 | 일치 수 | 파일 수 | 의미 |
| --- | ---: | ---: | --- |
| Go `Sizeof/Offsetof` | 200 | 64 | 고정 배치 또는 직렬화 가정 후보; rate-control 구조체 배치 단정 포함 |
| Go 포인터·`uintptr` 변환 | 208 | 65 | 수명 손실·폭 축소 후보; 정상적인 단기 주소 계산과 새 시험도 포함 |
| Go `unsafe` 연산 | 1,927 | 226 | 검토 범위이며 모두 결함이라는 뜻은 아님 |
| C 정적 배치 검사 | 85 | 8 | 대부분 원본 Win32 ABI 크기 고정; rate-control과 64바이트 카운터 단정 포함 |
| x86/ISA 표식 | 32 | 8 | 원본 x87 의미 주석과 `minimp3`의 ARM64 NEON 경로처럼 검토된 항목도 포함 |
| C 포인터·정수 캐스트 | 631 | 48 | 정규식 기반 후보; 수동 분류 필요 |
| 상수 오프셋 `unsafe.Add` | 213 | 40 | 구조체 필드 또는 원본 메모리 맵 접근 후보 |
| `import "C"` | 129 | 129 | CGo 경계 파일 수 |

이 수치는 렉시컬 검색 결과다. 주석·정상 코드가 포함될 수 있고 여러 줄 표현을 놓칠 수 있으므로 완료율로 사용하지 않는다. 각 후보를 `runtime-layout`, `legacy-abi32`, `file-wire`, `callback`, `false-positive` 중 하나로 분류해야 한다.

상위 집중 지점은 다음과 같다.

- Go 배치 검사: `server/player.go`, `client/drawable.go`, `legacy/memmap.go`
- Go unsafe: `legacy/common/ccall/ccall.go`, `common/memmap/nox/blobdata/blob_ptrs.go`, `legacy/GAME_data_init.go`
- C 정적 검사: `legacy/defs.h`
- C 포인터·정수 캐스트: `legacy/GAME4_3.c`, `GAME3_3.c`, `GAME5.c`, `GAME3.c`
- 상수 오프셋 접근: `audio_ail.go`, `server/script_vm_old.go`, `server/object_ai_path.go`, `xfer.go`

## 첫 64비트 컴파일에서 확인된 ABI 단절

Darwin/ARM64에서 서버를 실제 컴파일하면 `server` 패키지의 32비트 크기 검사에서 먼저 중단된다. 이 검사는 잡음이 아니라 C와 Go가 동일 메모리를 직접 해석한다는 안전장치다.

| Go 타입 | 원본 32비트 크기 | 첫 Darwin/ARM64 진단 | 현재 Darwin/ARM64 |
| --- | ---: | ---: | ---: |
| `ObjectIndex` | 16 | 32 | 32 |
| `Object` 본체와 확장 핸들 | 780 | 1,016 | 928 |
| `PlayerJournal` | 76 | 88 | 88 |
| `MinimapItem` | 16 | 32 | 32 |
| `EquipmentData` | 24 | 48 | 48 |
| `Player` | 4,828 | 6,136 | 6,136 |
| `NPC` | 1,316 | 2,592 | 2,592 |

표의 `ObjectIndex`는 이제 독립된 네이티브 사이드카에서만 사용하므로 크기 차이가 C 공유 `Object` 후속 필드를 밀지 않는다. `Object` 전체 928바이트 중 C와 공유하는 접두사 912바이트는 네이티브 C `nox_object_t`와 핵심 필드 오프셋이 일치하며, 나머지 16바이트는 Go 전용 핸들이다.

`Player`는 첫 포인터 전까지 배치가 같지만 `PlayerUnit` 뒤부터 어긋난다. ARM64에서 `info`는 2,185가 아니라 2,189, `Frame3596`은 3,596이 아니라 4,880, `Field4580`은 4,580이 아니라 5,880에 놓인다.

더 중요한 문제는 `Player.C()`와 `Object.CObj()`가 Go 구조체 주소를 그대로 C의 `nox_playerInfo*`, `nox_object_t*`로 넘긴다는 점이다. C 코드에는 여전히 `+276`, `+444`, `+2056`, `+3644` 같은 원본 바이트 오프셋 접근이 있다. 따라서 크기 검사와 C `_Static_assert`만 비활성화하면 컴파일 단계는 더 진행될 수 있어도 올바른 포트가 아니며, 런타임 메모리 손상을 만든다.

## 구조체 분리 원칙

각 구조체와 필드를 다음 세 영역 중 하나로 옮긴다.

1. `Legacy*32`: 원본 실행 파일 분석과 호환 검사용 고정폭 바이트 배치. 런타임 포인터를 넣지 않는다.
2. 네이티브 런타임 타입: Go/C의 실제 포인터, `size_t` 또는 Go `int`를 사용한다. 원본 바이트 오프셋을 API로 노출하지 않는다.
3. 파일·네트워크 DTO: 명시적인 little-endian 정수와 encode/decode 함수만 사용한다.

C가 장기간 보관해야 하는 Go 객체 참조는 `runtime/cgo.Handle`을 직접 와이어 형식에 넣지 않고, 세대 번호를 포함한 프로젝트 정수 핸들 테이블을 통과시킨다. C 할당 객체라면 네이티브 C 포인터를 사용할 수 있지만 파일·패킷·원본 ABI32 필드로 직렬화하지 않는다.

## 구현 우선순위

1. `Object`/`ObjectIndex`: 네이티브 맵 인덱스 사이드카와 명명 필드 C/Go 배치 대조는 완료했다. 동기화 표시, 상태 마스크, 활성 상태, 높이, 확장 상태, 애니메이션 프레임, 버프 상태, 수식어 적용, 질량·버프 읽기, NPC 색·장비 변경, nullable getter와 동기화 데이터 질의의 열아홉 객체 함수, 두 고정 시드 래퍼, 중요 패킷 상태 초기화·임계값 계산·플레이어 카운터 초기화를 복원하거나 원본 계약으로 고정했다. `004E4990` 직접 호출 그래프는 네이티브 폭으로 옮겼지만 보상 정의의 32비트 수식어 포인터 테이블과 `int` 객체 인수인 상위 호출자는 추적 항목으로 남는다. `004E4A90`의 두 XFer 함수와 `004E4B20`의 네 상위 장착 함수도 `int` 객체·업데이트 데이터 경로가 남는다. 다음 주소 순서 단위는 32개 rate-control 레코드를 재설정하는 `004E4EF0`이다.
2. 콜백과 함수 포인터: `Object` 후반의 init/collide/xfer/damage/update 포인터를 타입이 있는 디스패치 ID 또는 얇은 C thunk로 교체한다.
3. `EquipmentData`, `NPC`: 반복 배열이어서 포인터 폭 증가가 크게 누적된다. 데이터 ID와 런타임 참조를 분리한다.
4. `Player`, journal, minimap: `nox_playerInfo` 전체 캐스트를 없애고 남은 C 함수를 작은 필드 단위 API로 감싼 뒤 Go로 이식한다.
5. drawable·GUI·오디오 구조체: 같은 방식을 클라이언트 공유 구조에 적용한다.
6. `ccall`과 원본 메모리 맵: x86 함수 포인터 호출 및 주소 기반 전역 접근을 대상 독립 디스패치로 교체한다.

각 항목은 다음 게이트를 순서대로 통과해야 한다.

```text
32비트 배치 회귀 -> 64비트 C/Go 배치 대조 -> 단위·차등 테스트
-> 대상별 컴파일 -> QEMU/실기 시작 시험 -> 결정론 replay
```

## 현재 차단 상태

- Linux/386 기준선은 재현됐다.
- 첫 `ObjectIndex` 분리 후 Linux/386 클라이언트·HD·서버를 다시 빌드했다. 아홉 함수의 원본 계약을 고정한 깨끗한 커밋 `7351fb4bd`에서도 서버를 다시 링크했고, 산출물의 `-h` 시작 시험, Go 1.26.5와 `vcs.modified=false` 메타데이터 검사를 통과했다. 열 번째 함수 `004E4990`과 전체 직접 호출 그래프를 반영한 코드 커밋 `e7c3eecd8`에서 Linux/386 `server`와 `legacy` 전체 시험을 통과했다. `004E4A90`의 계약 시험은 `eb68babbf`, 구현과 직접 호출 경계 타입화는 `a358ea8eb`이다. 삭제됐던 `004E4A80`은 `d8a8d2db3`에서 복원했다. `004E4B20`의 계약은 `c52c35628`, C 경계와 호출자 정리는 `217a7e9f9`이다. nullable getter 다섯 개의 반환 폭·포인터 경계와 보호 CRC 호출부는 `16692f4f9`에서 정리했다. `004E4C90`의 원본 계약과 NaN 수정은 `5f08b3689`, CGo·직접 호출 경계 타입화는 `03f0d8259`이다. 고정 시드 래퍼 둘은 `cd06ffc3d`, 중요 패킷 상태 초기화와 할당 클래스 사이드카는 `728a4aed9`, 임계값 계산은 `c07c284a5`, 플레이어 카운터 초기화는 `a419c9882`에서 복원했으며 같은 전체 시험을 다시 통과했다. 이 단계에서는 제품 바이너리 해시를 아직 갱신하지 않았다.
